# newapi-auto-chicken-in

New API 系站点的自动签到工具。核心难点不在"发个 POST"，而在**过 Cloudflare** 和
**管好会轮转的凭据**——这两件事决定了它能不能天天跑得住。

支持两种登录方式：

| 方式 | 凭据 | 特点 |
|---|---|---|
| `newapi_cookie` | 完整 Cookie 头 | 静态凭据，配好就不用管 |
| `tabiai` | `new_api_refresh` cookie | 凭据**按代次轮转**，每轮必须回写，还需要真实浏览器提供的 Turnstile token |

## 过盾思路

一条按代价从低到高排的策略链，每层失败才往下走，成功立刻收工：

| 层 | 做法 | 代价 |
|---|---|---|
| **S0** | 用缓存的 `cf_clearance` + UA + 出口 IP 直接发 HTTP | 几乎为零 |
| **S1** | `curl_cffi` 伪装 TLS/JA3 指纹裸发 | 一次请求 |
| **S2** | 起浏览器等 Cloudflare 自解，收割 cookie 回来重发 | 几秒~几十秒 |
| **S3** | 自解不过时先按预设位置点复选框，没生效才让 AI 看截图代为点选 | 预设点击零成本；AI 是兜底，有次数上限 |
| **S4** | 不把 cookie 搬回 HTTP，直接在浏览器页面里发签到请求 | 复用 S2/S3 的浏览器 |
| **S5** | 人工兜底：有头浏览器等你手动过，过完存 profile | 需要你在场 |

S4 存在的理由值得单说：S2/S3 过盾成功后，浏览器拿到的 cookie 搬回 `curl_cffi`
还灵不灵是**不确定**的——指纹环境变了，Cloudflare 完全可能不认。S4 绕开这个不确定
性，既然浏览器已经过了盾，就在同一个上下文里把签到发掉。

拦截识别不靠关键词匹配，是**状态码 + 响应头 + 正文特征三路交叉**，并区分「可过的
质询」和「WAF 硬封禁」——后者重试毫无意义，直接报错让人去换住宅代理。

重试也分两类：**盾类失败**（被质询拦住、拿不到 token）换出口 IP + 重开浏览器、
**不限次数**，因为这类问题换个 IP 往往就过了；**计次失败**（网络抖动、响应看不懂）
才有次数上限。

## 三种跑法

```bash
# 1) 本地 CLI
pip install -r requirements.txt
python -m camoufox fetch          # 首次需要，下载过盾用的浏览器
cp config.example.json config.json
python main.py -v

# 2) Windows 桌面版（PySide6 面板 / 后台服务）
python desktop.py                 # 图形面板
python desktop.py --daemon        # 后台常驻

# 3) GitHub Actions（见 .github/workflows/）
#    把 config.json 的 base64 放进 CONFIG_JSON_B64 secret 即可
#    checkin.yml      北京 04:00 签到，账号多时自动切片并行，跑完只发一封汇总邮件
#    proxy-sweep.yml  北京 03:00 代理体检，实测结果回传平台，供一小时后的签到优选
#    test.yml         每次 push 跑 pytest / go test / vue-tsc 三端回归
```

另有一个**配置管理平台**（`server/` + `web/`，单二进制含前端）：网页端管账号与凭据、
检测 Cookie 可用性、维护代理池、以及下面要讲的凭据保活。客户端通过 `config_sync`
从它拉配置、把轮转后的新凭据回写给它。

## 主要能力

- **代理池**：自动抓取+测通，签到失败按「代理不通」还是「出口 IP 被拦」分别记账，
  跑完把每个 IP 的真实成败回传平台供优选排序。同一出口默认最多服务 4 个账号
  （`proxy_pool.max_accounts_per_ip`），预取量按这个上限折算，几百个账号也不用抓
  几百个代理。平台刷新时会把库里还存活的老代理一起复测，能通的保留并与新测通的合并
  去重 —— 免费源列表天天变，只测新抓的会让「还通着但今天没被源收录」的出口凭空消失
- **代理体检**：签到前一小时（北京 03:00）单独跑一趟，把平台上的存活代理从
  **Actions 自己的出口**全量实测再回传。平台自带的 refresh/speedtest 走的是服务器
  出口，而代理商封机房 IP 段是常事 —— 服务器那边通的代理到了 Actions 手里可能全是
  废的，光靠平台自测选出来的「最优」名不副实。入口是 `main.py --proxy-sweep`
- **分片并行**：账号按每片 N 个切开并行跑，各片不重叠、各自维护代理池
- **邮件日报**：HTML 汇总表 + 按站点的额度总览（下面第二、三章详说）
- **凭据保活**：定时主动 refresh 让代次滚动，避免隔天被判重放（下面第一章详说）
- **配置加密**：`config.json` 可 AES-GCM 加密落盘

## 一、TaBiAI 凭据保活

### 1.1 要解决的问题

`new_api_refresh` 的结构是 `<sid>.<secret>`：

| 部分 | 寿命 | 行为 |
|---|---|---|
| `sid` | 30 天不变 | 会话标识 |
| `secret` | **按代次轮转** | 每次 refresh 成功就下发下一代 |

服务端实现的是 refresh token rotation + 重放检测。同一代 secret 只有**分钟级宽限
窗口**，窗口内重复用是幂等的（返回同一个新值）；超出窗口后旧代作废，再用会先
`401 AUTH_UNAUTHORIZED`，一旦被判定为旧代重放，**整条会话被撤销**
（`401 AUTH_SESSION_REVOKED`），只能重新签发。

两种失效都能自救：账号填了 `github_user_session` 时，签到发现 refresh 被拒会当场走
GitHub OAuth 三步**重新签发一条**（走该账号同一个代理出口），落盘并回写平台后重试本
轮。每个账号一轮只签发一次 —— 签发换出全新 sid、把上一条当场作废，失败了再签只是继
续耗 GitHub 那把会话的信誉。没填 `user_session`、或连它也失效时判负，原因写进汇总邮件。

签到一天只跑一次，中间十几个小时那一代一直躺着不动。这段时间里任何一个"第三方"
——本机 daemon、网页端的凭据检测、另一台机器——碰一下，平台手里这代就作废了，
第二天签到拿着它去撞重放检测，账号直接被打死。

保活按固定间隔主动 refresh 一次并**立刻落库**，把这个暴露窗口从十几小时压到一个
刷新间隔之内。

### 1.2 为什么放在配置管理平台而不是 Actions

- 平台常驻，凭据就在它自己的 SQLite 里，轮转后直接 `UPDATE`，**没有「回写可能
  失败」这一环**。Actions 那条路要靠 HTTP 回写平台，多一个会断的地方。
- cron 表达不出严格的 90 分钟间隔（90 不整除 60 和 24），`time.Ticker` 一行就够。
- Actions 的 runner 是一次性的，`data/sessions.json` 刻意不缓存（公共仓库的
  Actions 缓存对外可读），本地落盘那份下一轮就没了。

### 1.3 两条硬规则

**签到与保活双向避让。** 保活的 refresh 和签到的 refresh 抢同一条 sid，撞上是把账号
打死，不是「这次保活失败」那么轻。所以两个方向都要堵：

- **保活让签到**：判活直接复用 `run_state` 的心跳机制，签到在跑就跳过这一轮，把
  `skipped_by_checkin` 置为 true，界面上能解释为什么这一轮没刷。
- **签到让保活**：只挡一个方向不够——保活跑到一半、签到才启动的那个窗口（几十秒到
  几分钟）照样会撞。为此保活自己也占住 `run_state` 锁（source 记为
  `tabiai-keepalive`），签到客户端开跑前查一次 `GET /api/run-state`，发现是保活持锁
  就等它跑完，**上限 5 分钟**，超时带告警继续——保活卡死不能把签到一起拖死。

判定必须落在 **source 等于 `tabiai-keepalive`** 上，不能按「有没有人持锁」判。
`run_state` 是引用计数锁，Actions 分片并行时几个 job 同时持锁是常态，按持锁判会让
分片互相等待直接死锁。同理，纯 Cookie 账号的轮次压根不用等——没有 sid 就没有代次冲突。

查锁失败一律当成没锁：平台不可达时不该连签到都做不了。

> **已知限制**：`run_state` 是单行表，只记一个 source。若签到客户端超时放行后仍去调
> `POST /api/run-state/start`，`holders` 会变成 2（锁本身仍然有效），但 `source` 会被
> 覆盖成客户端自己的名字，此后从 `/api/run-state` 和网页端 409 提示里看不出「保活也
> 在跑」。只影响观测，不影响互斥正确性。

**凭据失效就暂停该账号。** 判定为 `invalid` 后停止自动刷新——继续刷既救不回来，
还会把日志刷满。恢复条件是**凭据被改过**：服务端记下暂停那一刻的凭据值，下一轮
发现库里的值不同了（重新签发或手动粘贴）就自动恢复并刷一次。首尾空白不算被编辑，
免得复制粘贴带个换行就误恢复。

### 1.4 代理策略

刷新走的是和网页端「TaBiAI 凭据检测」**完全同一条路**（`runCookieTestPass` +
`checkTabiAICookie`），所以判定口径与代理行为天然一致，不存在两份实现走歪。

代理故障会自动换 IP：

- **链路类失败**（代理不通、CDN/WAF 挡在门外）换一个代理接着来，池子掏不出新地址
  就停。这类失败在服务端是 `abnormal` 状态 + 内部 `retryable` 标记，**没有独立的
  `proxy_issue` 状态词**。
- **非代理失败**（凭据失效、响应异常）不重试。换 IP 也是同样结果，而凭据失效本来
  就要走暂停逻辑。
- 5 轮上限兜住「池子有几百个地址」的情况，免得一个账号吃掉整轮的时间预算。发牌
  拿到空串（池空）时立刻停，否则下一轮还是直连、结果不会变。
- 一个账号累计换满 10 个 IP 后，换 IP 会**优先复用本轮签到成功过的出口**（而不是
  继续撞没试过的）：盾/源站拦的往往是某个具体出口的声誉，换成已证明可用的地址往往
  直接就过了。成功出口若再失败仍会被拉黑，不会反复踩同一个坑。

账号自带代理时沿用它自己的，不从池里换——那是用户显式指定的出口。

**但 refresh 一旦推进了代次，重试就必须立刻停。** 拿旧代换个出口再来一次，正是重放
攻击的教科书特征，而安全窗口只有 20 秒起（见 `docs/签到原理.md` 的实测）；换一轮代理
光建连就可能吃掉这点余量。判据用的是 `Set-Cookie` 里有没有 `new_api_refresh` ——
**只有源站会下发它，CDN 的挑战页不会**，所以它同时回答了两件事：新代次要不要落库，
以及手里的旧代快照还能不能用。抠到新代次就落库并当场关掉 `retryable`。

这条判据还顺手堵了一个静默丢代次的坑：body 读失败或响应被判成挑战页时，早退分支曾经
直接返回，而 `Set-Cookie` 明明已经躺在 header 里。那种情况下站点侧代次已经推进、平台
却停在旧代，下一轮保活必然撞重放。现在 header 一到手就先抢救代次，之后无论从哪个分支
返回都带着它走。

`client.Do` 直接报错（连 header 都没有）时无从抢救，只能按错误类型分流：拨号阶段失败
（代理连不通、DNS 挂了、`proxyconnect`）说明请求从未到达源站、代次不可能推进，照常换
代理重试；超时或连接中途断开则按最坏情况处理，本轮直接放弃 —— 保活 90 分钟一轮，少刷
一次毫无损失，赌错一次却要重新签发所有账号。

### 1.5 配置与界面

网页端侧边栏「凭据保活」。间隔被夹在 **15~720 分钟**（默认 90）：刷太勤只是多消耗
代次，超过半天就失去压缩窗口的意义。关闭用开关表达，不要把间隔填 0。

协程按 60 秒节拍巡检而不是直接睡满间隔——这样你在网页端改小间隔能立刻生效。
panic 被兜住后 60 秒重进循环，不让协程静默消失（照代理池后台刷新那套来）。

### 1.6 「已换代次」这一列怎么读

界面上每个账号有一个「已换代次」（`rotated`）。它表示这一次站点有没有在响应里下发
新的 `Set-Cookie`。

- 状态正常但显示「否」→ **正常现象**。宽限窗口内 refresh 是幂等的，站点不换新值。
- **长期都是「否」** → 值得怀疑回写链路：要么站点行为变了，要么写库那一步在静默
  失败（后者会在服务端日志里留 `新凭据落库失败`）。

只要站点下发了新值，**无论本次判定成败**都会立刻写回 `accounts[].cookie`。这条不能
省：判定失败但代次已经换了的情况是存在的，不落库下一次必然踩旧代。

## 二、额度显示与按站点总览

### 2.1 邮件里的「剩余额度」是什么

以前那一列显示的是 `quota_awarded`——**本次签到奖励**，不是余额。三种情况下它都是
空的：

1. 今日已签时签到接口压根不返回奖励额度
2. `user_id` 第一次跑完就缓存了，之后 `/api/user/self` 再也不会被调用，余额没来源
3. 有些站点签到成功也不返回 `quota_awarded`

所以那一列经常空着，看着像功能坏了，其实是查的东西不对。

现在改成**签到有结论后补查一次 `/api/user/self`**，取 `data.quota` 作为账户剩余额度：

| 路径 | 做法 |
|---|---|
| `newapi_cookie`（S1/S2） | runner 用同一个 client 调 `fetch_self` |
| `tabiai` | `TabiAIClient` 在 access_token 还在手上时查 |
| S4（浏览器内直发） | 页内 `fetch` 查一次，用的是同一个浏览器上下文 |
| `--dry-run` | 复用为验证连通已经查过的那次结果，零额外请求 |

只在签到成功 / 今日已签时查：失败的账号连凭据都可能是坏的，再打一次也是白费。
全程异常吞掉只留 debug——余额是邮件里多一列，不能因为它把一个已经签成功的账号
弄成失败。

### 2.2 为什么 S4 不读页面上的数字

S4 那条路已经在浏览器里了，直觉上读 DOM 更省事。但站点是 React SPA，余额显示在
`/profile` 的卡片里，DOM 结构和 class 名随前端版本变（chunk 名都带 hash），一次
发版就可能读空。`data.quota` 是后端契约，稳得多。页内 `fetch` 拿到的也是「网页
自己的数据」——同一个上下文、同一份 cookie 和指纹，只是绕过了 DOM 这层易碎的中间物。

### 2.3 金额换算

额度在接口里是内部整数，换算成站点展示的 `$` 要除以 `quota_per_unit`。这个值从
`/api/status` 探一次后缓存进 `sessions.json`（站点级属性），探不到退回 500000
（New API 上游默认值）。**不写死**是因为不同 fork 的换算率不一定相同。

换算率逐行跟着结果走，所以几个站点混在一封邮件里也各按自己的比例折算。

额度列的文案是 `$12.34（+$5.20）`：余额为主、本次奖励跟在括号里。三个边界特意
区分开：

- 余额真的是 0 → 显示 `$0.00`（账户没钱了）
- 余额没查到但有奖励值 → 显示 `+$5.20`（退一步给点信息，整列空着最没用）
- 两个都没有 → 显示 `-`

### 2.4 额度总览：还能发多少次请求

邮件底部按站点分组，各站小计余额 + 每个模型的单价与可发次数 + 全局合计。

定价来自各站点的 `GET /api/pricing`。这个接口**不需要 cookie**，但裸请求会吃
Cloudflare 的闭门羹，必须走 `curl_cffi` 的指纹伪装（和 S1 快路径同一套
impersonate）。请求也带代理，规则和签到一致：代理故障无限换（池子掏不出新地址为止），
非代理原因最多 5 次——后者换 IP 大概率还是一样，多试只是浪费时间。

**次数是精确值，不是估算。** 2026-08 实拉 `gorouter.app` 与 `tabitoken.com` 确认，
两站的 opus 模型全是 `quota_type: 1`（按次计费），`model_price` 就是每次请求的美元
单价，所以 `次数 = 余额 ÷ 单价`，向下取整（半次请求发不出去）。

对按 token 计费的模型（`quota_type: 0`）只标计费方式和倍率，**不编一个假设的 token
数糊弄人**——那种模型没有「一次请求」的价格这个概念。

其他约定：

- **定价每轮实时拉、不落缓存**。站点随时可能调价，用昨天的价格算出来的次数是假的。
  同一站点只拉一次（域名去重），不会因为账号多而重复打接口。
- 只统计模型名含 `opus` 的条目。站点以后加了别的模型不会混进来。
- 有账号没查到余额时，合计与次数会标成**下限**，总计后面加个「起」字。
- 拉定价失败、被盾拦、返回非 JSON 一律降级成「定价表暂不可用」，余额汇总照旧；
  整个总览异常也只是省掉这一段，绝不拖垮发信。
- 按默认分组（`group_ratio` 里的 `default`）价格计算。

## 三、一天只收一封邮件

账号切成多片并行后，每片是独立进程，各自只知道自己那几个账号的结果。早期版本每片
跑完都自己发一封，一天要收好几封拼图；让某一片代表大家发也不行——任何一片都只
看得见自己的结果。

现在拆成两段：

1. 分片用 `--summary-out` 把结果写成 JSON 并**不再自己发邮件**
2. 汇总 job（`needs: [plan, checkin]`，`if: always()`）下载全部
   `checkin-summary-*` artifact，用 `--send-summary` 递归合并后只发一封

结果只能走 artifact 传，**不能走 job output**：带账号名的 output 会被 GitHub 判
「可能含 secret」而整个跳过（`Skip output '<name>' since it may contain secret`），
下游 `fromJson('')` 直接报错。matrix 就在这上面栽过一次，所以矩阵现在也是写死的
字面量 `[1..8]`，超出实际片数的 job 靠每步的 `if` 秒退。

**缺片不静默。** 每片把自己的 `I/N` 写进文件内容（不靠文件名，artifact 下载会套一层
目录），合并时算出预期几片、实到哪几片，缺的片号直接写进邮件正文，并走橙色警示块
而不是灰色小字——分片被 OOM 或超时打断时，不能让那批账号悄无声息地消失。

其他防御：坏 JSON 只跳过那一个文件；缺 `name`/`status` 的行丢掉；未知字段忽略；
`dry_run` 只在所有片都是连通性检查时才标（混合按真实签到算，免得主题误标）。
分片结果落盘失败只 WARN——这一轮真正的产出是签到，不该被写文件的错抹掉。

## 四、已知限制

| 限制 | 说明 |
|---|---|
| 保活治症不治根 | 它把暴露窗口压到一个间隔之内，但如果真有第三方在消耗代次，问题只是更难触发而不是消失 |
| 保活期间的请求量 | 每 90 分钟一轮，一天 16 次 refresh，比原来（一天 1 次）频繁得多。若站点对 refresh 有频率限制需要调大间隔 |
| 额度查询的额外请求 | 每个账号签到后多一次 `/api/user/self` |
| 分组倍率 | 按 `default` 分组计算。账号若在别的分组，价格会有偏差 |
| 定价接口的可用性 | Actions 是数据中心 IP，`/api/pricing` 可能被盾拦得更严，那时总览只有余额没有次数 |

## 五、排查指引

### 凭据隔天失效

先确认错误码，两者含义完全不同：

- `AUTH_UNAUTHORIZED` → **当前代次失效**。说明有别的东西消耗了代次。查：是否有第二个
  执行者（本机 daemon / 定时任务）？平台的拉取接口和回写接口读写的是不是同一份数据？
- `AUTH_SESSION_REVOKED` → **整条会话已废**。确实发生了旧代重放，或者你在浏览器点过
  「退出其他会话」。只能重新签发。

最快的自查：签到成功后去平台看那个账号的凭据值，**点号后面那一半和之前是不是不一样了**。
变了说明回写通了，问题在别处；没变就是回写这一环断了。

### 额度列是 `-`

按上面 2.1 的表对一下这个账号走的是哪条路径。落到 S4 且页内查询也被拦时会是 `-`；
签到本身失败的账号不查余额，也是 `-`。开 `-v` 看 debug 日志里的
`未能取到剩余额度` 或 `页内查余额失败`。

### 总览里没有次数

说明定价表没拉到。日志里搜 `拉定价表`，会写明是 HTTP 非 200、非 JSON（被盾）
还是代理问题。代理问题会自动换 IP 重试，非代理问题 5 次后放弃。

### 邮件收到多封

检查分片是否真的用了 `--summary-out`，以及 `notify` job 有没有跑。如果某片没写出
artifact，汇总邮件里会标出缺片。
