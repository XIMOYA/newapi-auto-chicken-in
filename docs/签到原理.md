## 二、鉴权架构

### 2.1 为什么不能只带 cookie 打接口

站点采用「长期 refresh cookie + 短期内存 access token」双层结构。业务接口只认
`Authorization` 头，不认 cookie：

```
GET /api/user/checkin?month=2026-08     （仅带 cookie）
-> 401 {"code":"AUTH_UNAUTHORIZED","message":"无权进行此操作，access token 无效","success":false}
```

前端源码里的拦截器印证了这一点：

```js
// static/js/index.*.js
c.interceptors.request.use(e => {
  let t = l.n.getState().auth.accessToken;
  return t && (e.headers.Authorization = `Bearer ${t}`), e;
});
```

access token 只存在 zustand 内存 store 里，不落 localStorage，所以刷新页面必须重新换取。

### 2.2 换取 access token 的端点

```
POST /api/user/auth/refresh          （仅需 cookie，可选头 X-Auth-Session: <sid>）
-> 200 {"data":{
          "access_token":"eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9...",
          "access_expires_at": 1786976078,
          "user": {...}, "session": {...}
        },"success":true}
```

- 返回的 JWT 有效期约 **300 秒**
- 所以脚本不能缓存 token，只能缓存 cookie、每次现换

### 2.3 refresh cookie 的结构

```
Set-Cookie: new_api_refresh=<sid>.<secret>;
            Path=/api/user/auth; Expires=<30天后>; Max-Age=2591999;
            HttpOnly; SameSite=Strict
```

```
new_api_refresh = 930311ee-c5ea-4a47-aff1-c5ceb8c9db1d . wQB9MW0kxiBew1WOTTdRLWiU...
                  └──────────── sid ───────────────┘     └────── secret ─────────┘
                  会话标识，30 天不变                       真正的凭据，按代次轮转
```

注意 `Path=/api/user/auth`：这个 cookie 只会发给换令牌的端点，不会发给业务接口。脚本手工
构造请求时必须按这个 path 设置，否则不会被带出去。

单独持有 sid **无法鉴权**，必须 `sid.secret` 完整值。

### 2.4 轮转规则与重放检测（最容易踩死的地方）

服务端实现的是 **refresh token rotation + 重放检测**，实测出的行为模型：

1. 每次 `refresh` 成功后，服务端会下发**下一代** secret，sid 不变
2. 同一代 secret 在**短宽限窗口内**可以重复使用，且幂等 —— 返回的下一代值完全相同
3. 超出宽限窗口后旧代作废，此时再用旧代**直接判重放**，会话立刻被撤销
   （`401 AUTH_SESSION_REVOKED`），此后该 sid 下所有代次全部失效
4. 代次数量**没有上限**，链能一直往下滚；卡的是 sid 自己的 30 天寿命

> **宽限窗口实测（2026-08-23，tabitoken.cc）**：窗口落在 **(20s, 45s]** 区间。
> 旧代放 20 秒后重放仍然 `HTTP 200` 且幂等返回同一个新代；放 45 秒后重放直接
> `401 AUTH_SESSION_REVOKED`。
>
> **没有 `AUTH_UNAUTHORIZED` 这个温和中间态** —— 出窗即判重放，一步到死，不存在
> 「先警告再撤销」的缓冲带。早期文档写的两段式行为是错的。
>
> 这个数字有工程后果：`http.timeout` 默认就是 **20 秒**，和窗口下界撞在一条线上。
> refresh 超时一次就烧光整个安全窗口，此时换 IP 重试等于拿整条会话赌运气。所以客户端
> 的 refresh 用独立的 8 秒超时（`tabiai.REFRESH_TIMEOUT_SECONDS`），并按 15 秒的
> 悬空预算（`INFLIGHT_BUDGET_SECONDS`）拒绝超期重试，预算记在 `sessions.json` 里
> 跨进程生效 —— Actions 被强杀是常态，纯内存计时挡不住「进程死了、下一轮捡起旧代接着刷」。
>
> **但「网络失败」必须按阶段分开看**，否则会误杀。判据是「请求字节有没有可能已经写出去」：
>
> | 阶段 | curl 码 | Go 侧对应 | 代次 | 处置 |
> |---|---|---|---|---|
> | 代理/域名没解析出来 | 5 / 6 | `*net.DNSError` | 一定没动 | 销账，照常换 IP |
> | TCP 握手失败 | 7 | `OpError{Op:"dial"}` | 一定没动 | 同上 |
> | 连接阶段超时 | 28 + `Connection timed out` | `OpError{Op:"dial"}` | 一定没动 | 同上 |
> | TLS 握手失败 | 35 | `tls.RecordHeaderError` 等 | 一定没动 | 同上 |
> | 代理隧道失败 | 97 | `OpError{Op:"proxyconnect"}` | 一定没动 | 同上 |
> | 整体超时 | 28 + `Operation timed out` | `context.DeadlineExceeded` | **可能已推进** | 留账，停手 |
> | 发/收失败、空响应 | 18 / 52 / 55 / 56 | `OpError{Op:"read"/"write"}` | **可能已推进** | 留账，停手 |
>
> 第一版没做这个区分，把所有网络错误都算成「可能已发出」，结果代理池里的死地址直接把
> 签到打瘫 —— 8 秒连接超时换两次 IP 就累计超过 15 秒预算，账号连站点都没碰到就被闸门
> 拦死。判断方向从严（拿不准算危险）是对的，但**从严不等于不分阶段**。
>
> 连接阶段另给 4 秒上限（`REFRESH_CONNECT_TIMEOUT_SECONDS`），让死代理尽快暴露，
> 别把 8 秒整体预算耗在建连上。

对应实测：

```
# 宽限窗口内连续三次用同一代 —— 全部成功，且下发的新值完全一致
[轮次1] refresh -> HTTP 200  下发新 cookie ...4fbd3b99c045dbfb
[轮次2] refresh -> HTTP 200  下发新 cookie ...4fbd3b99c045dbfb
[轮次3] refresh -> HTTP 200  下发新 cookie ...4fbd3b99c045dbfb

# 隔了数分钟后再用同一代 —— 会话直接被撤销
[旧cookie refresh] 401 {"code":"AUTH_SESSION_REVOKED","message":"Unauthorized"}
```

窗口边界的二分探测（2026-08-23，牺牲一条会话换来的）：

```
# 旧代放置 20s 后重放 —— 还在窗口内，幂等返回同一个新代
[推进]     HTTP 200  新代尾部=90729778820259b0
[重放旧代] HTTP 200  返回代尾部=90729778820259b0

# 旧代放置 45s 后重放 —— 直接撤销，没有 AUTH_UNAUTHORIZED 过渡
[推进]     HTTP 200  新代尾部=149b473131d35328
[重放旧代] HTTP 401  code=AUTH_SESSION_REVOKED
```

**结论：不存在「写死一份 cookie 长期用」的方案。** 脚本每轮必须把响应里的
`Set-Cookie` 落盘，下一轮用最新代次。这是硬要求，不是优化项。

另外：用户在浏览器里点「退出其他会话」会立即撤销脚本那条 sid，需要重新签发。

## 三、签到接口

前端 chunk `5851.*.js` 里的两个函数，是接口的一手依据：

```js
// 查询当月签到状态
async function H(e) { return (await S.FH.get(`/api/user/checkin?month=${e}`)).data }

// 执行签到，turnstile 为空时退化成不带查询串
async function I(e) {
  let s = e ? `/api/user/checkin?turnstile=${encodeURIComponent(e)}` : "/api/user/checkin";
  return (await S.FH.post(s)).data;
}
```

```
            "total_checkins": 3,
            "total_quota": 11938895,     // 累计获得，= $23.88
            "records":[
              {"checkin_date":"2026-08-17","quota_awarded":4874773},

              {"checkin_date":"2026-08-11","quota_awarded":3983224}

```

### 3.2 执行

```
POST /api/user/checkin?turnstile=<真实 Turnstile token>
Authorization: Bearer <JWT>
```

注意：**业务失败也返回 HTTP 200**，成败看 body 里的 `success` 字段。

已知的几种返回：

| turnstile 参数 | 响应 body | 含义 |
|---|---|---|
| 不带 / 空串 | `{"message":"Turnstile token 为空","success":false}` | 没到校验阶段 |
| 伪造值 `test123` | `{"message":"Turnstile 校验失败，请刷新重试！","success":false}` | 服务端真的去 CF 验了 |
| 真实 token（当天已签） | `{"message":"今日已签到","success":false}` | **已穿透 CF，进入业务层** |
| 真实 token（当天未签） | `{"data":{...},"success":true}` | 签到成功，额度到账 |

第三行是判断「链路是否打通」的关键信号：报错从 Turnstile 变成业务提示，说明 token 被
Cloudflare 认可了。

## 四、Turnstile 这一关

### 4.1 为什么绕不过

服务端拿到 `turnstile` 参数后，会向 Cloudflare 的 `siteverify` 接口验证真伪。token 由
**Cloudflare 用自己的私钥签发**，本地无法伪造 —— 上表第二行就是证据。

同时它**不是图形验证码**，没有任何可供识别的图片：Turnstile 在 iframe 里运行混淆 JS，
采集 Canvas/WebGL 指纹、字体、事件时序等上百项环境特征，与 CF 边缘完成一次密码学
挑战应答，通过后才签发 token。因此「用 AI 识图过验证」在原理上不适用。

### 4.2 为什么自动化浏览器拿不到

| 环境 | 结果 |
|---|---|
| 无头 Chromium | `error-callback: 300010`，挑战执行失败 |
| Playwright 启动的有头 Chrome（已抹 `navigator.webdriver`） | `Error: 600010`，挑战 iframe 压根不渲染 |
| Playwright 启动 + 读站点自带 widget | 60 秒 `cf-iframe=0`，hidden input 一直空值 |

网络层是通的，抓包能看到挑战资源全部 200，唯独设备证明端点 401：

```
302 /turnstile/v0/api.js?render=explicit
200 /turnstile/v0/g/aae2b9a1c261/api.js
200 /cdn-cgi/challenge-platform/h/g/turnstile/f/av0/rch/...
200 blob:https://challenges.cloudflare.com/68947cca-...      ← worker 已创建
200 /cdn-cgi/challenge-platform/h/g/ci/...                   ← 指纹已上报
401 /cdn-cgi/challenge-platform/h/g/pat/...                  ← PAT 设备证明失败
```

`pat` 即 Private Access Token。CF 拿不到设备背书 + 检测到自动化痕迹，就不再下发挑战，
直接判 `600010`。所以问题不是「识别不出来」，是**根本没让你开始挑战**。

### 4.3 可行解：CDP 接管用户自己启动的 Chrome

不要用 `playwright.launch()`，而是让 Chrome 以调试端口正常启动，再用 CDP 连上去：

```bash
chrome.exe --remote-debugging-port=9222 \
           --user-data-dir=<独立目录> \
           --no-first-run --no-default-browser-check \
           https://tabitoken.com/sign-in
```

```python
b = p.chromium.connect_over_cdp("http://127.0.0.1:9222")
page = next(x for x in b.contexts[0].pages if "tabitoken.com" in x.url)
```

这个进程没有 `--enable-automation` 等自动化标志，`navigator.webdriver` 为 `false`，
指纹与用户日常浏览器一致。实测**无需任何人工点击**，Turnstile 自动完成并把 token
写入隐藏域：

```python
document.querySelector('input[name="cf-turnstile-response"]').value
# -> 816 字符的真实 token
```

需要新 token 时，在页面上下文调 `window.turnstile.reset()` 即可重跑挑战。

## 五、完整链路

```
        ┌──────────────────────────────────────────────┐
        │  落盘的 new_api_refresh（sid.secret，30天）    │
        └───────────────────┬──────────────────────────┘
                            │ cookie，Path=/api/user/auth
                            ▼
              POST /api/user/auth/refresh
                            │
              ┌─────────────┴─────────────┐
              ▼                           ▼
      access_token（JWT，300秒）    新一代 cookie → 立即覆盖落盘
              │
              │        ┌───────────────────────────────────┐
              │        │ 真实 Chrome（CDP 9222 接管）        │
              │        │ 读 input[name=cf-turnstile-response]│
              │        └──────────────┬────────────────────┘
              │                       ▼
              │              Turnstile token（816 字符）
              ▼                       │
        POST /api/user/checkin?turnstile=<token>
        Authorization: Bearer <JWT>
                            │
                            ▼
              success=true → 额度入账（$5 ~ $10 随机）
              success=false + "今日已签到" → 当天重复
```

## 六、获取初始 cookie

首次或会话被撤销后，需要重新签发。走 GitHub OAuth 三步（该站 `github_oauth: true`，
`github_client_id: Ov23liDcLFM2IEijn5pH`）：

```
1) POST /api/oauth/state   {"provider":"github","intent":"login"}
   -> {"data":{"flow_token":"<state>","expires_at":...}}

2) GET https://github.com/login/oauth/authorize
       ?client_id=<client_id>&state=<state>&scope=user:email
   带 GitHub 的 user_session cookie，已授权过的应用会直接 302
   -> Location: https://tabitoken.com/oauth/github?code=<code>&state=<state>

3) GET /api/oauth/github?code=<code>&state=<state>
   -> Set-Cookie: new_api_refresh=...   ← 落盘这个
```

第 1 步和第 3 步必须在同一个 HTTP session 内完成（state 与会话绑定）。

每次走完这三步都会创建一条**新的 sid**，与用户日常浏览器的会话互不影响，因此给脚本单开
一条会话是安全做法。

## 七、写脚本时必须守住的几条

1. **cookie 每轮落盘**。`refresh` 后立刻把新值写回存储，绝不能"更新一半又用回旧的"，
   那等于重放，会把整条会话打死。
2. **不要缓存 access token**。只有 300 秒，每次现换成本极低。
3. **turnstile token 是一次性的**，且有效期很短，取到后要立刻用。
4. **Turnstile 有频率限制**。20 分钟内反复 `reset()` 会拿不到新 token（实测连续第 2、3 次
   等 150 秒仍为空）。真实场景每天一次，不受影响；调试时要控制频次。
5. **先查后签**。先 `GET` 看 `checked_in_today`，为 true 就直接退出，别浪费 turnstile 配额。
6. **业务失败也是 HTTP 200**，判定必须读 `success` 字段，不能只看状态码。
7. **不要拿脚本的 sid 在浏览器里登录**，浏览器会自动推进代次，导致脚本下次踩到旧代。

## 八、部署限制

| 方案 | 可行性 |
|---|---|
| 本机 Windows + 真实 Chrome + 定时任务 | 可行，已验证 |
| GitHub Actions / 纯服务器无头 | **不可行**，Turnstile 拒绝下发挑战 |
| 服务器 + xvfb 虚拟显示 | 未验证，机房 IP + 自动化指纹大概率仍被拒 |
| 打码平台（2captcha / CapMonster 等） | 可行但需付费，约 $0.002/次 |

因此当前推荐形态：**跑在本机、依赖一个常驻的调试端口 Chrome 的定时脚本**。
